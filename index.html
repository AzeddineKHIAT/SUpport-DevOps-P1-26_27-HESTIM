I.1 · Comprendre la démarche DevOps

DevOps : une définition

DevOps est une démarche qui rapproche le développement (Dev) et l'exploitation (Ops) pour livrer plus souvent et de façon plus fiable, grâce à la collaboration, à l'automatisation du trajet du code jusqu'à la production, et à la mesure continue.

DevOps, c'est…

  • une culture de responsabilité partagée
  • des pratiques : intégration et déploiement continus, tests automatisés, supervision
  • des outils au service de ces pratiques : Git, pipelines, Docker…

DevOps, ce n'est pas…

  • un logiciel que l'on installe
  • seulement un intitulé de poste
  • « supprimer les administrateurs »
  • « aller vite sans tester »

Origine : Patrick Debois, administrateur et consultant belge, veut appliquer l'agilité à l'exploitation. Il organise les premiers DevOpsDays à Gand en 2009 : le mot « DevOps » est né.

🎙️ Ce que je peux dire

« DevOps n'est pas un logiciel : on ne “télécharge” pas DevOps. C'est d'abord une culture : Dev et Ops partagent la responsabilité de ce qui tourne en production. Ensuite des pratiques, comme l'intégration continue ou la supervision. Et enfin des outils, dont Docker. Retenez cet ordre : culture, pratiques, outils. »

I.1 · Comprendre la démarche DevOps

Pourquoi les entreprises ont adopté DevOps

45 min

Knight Capital, 2012. Une nouvelle version est installée à la main sur 8 serveurs, mais un serveur est oublié. L'ancien code passe des millions d'ordres de bourse non voulus : plus de 460 millions de dollars perdus en 45 minutes.

Source : SEC, décision Knight Capital Americas LLC, 16 octobre 2013.

11,6 s

Amazon, 2011. À la même époque, Amazon met en production en moyenne une modification toutes les 11,6 secondes, grâce à des déploiements automatisés.

Source : Jon Jenkins (Amazon), « Velocity Culture », conférence Velocity 2011.

La différence n'est pas le talent des ingénieurs : c'est la manière de livrer. Livraisons manuelles = risque ; livraisons automatisées, petites et fréquentes = maîtrise.

🎙️ Ce que je peux dire

« Deux histoires vraies. Knight Capital : une installation manuelle oublie un serveur sur huit ; 460 millions de dollars perdus en 45 minutes. Amazon, à la même époque : une modification toutes les 11,6 secondes, sans casser son site. Les deux entreprises avaient d'excellents ingénieurs. Ce qui change, c'est la façon de livrer. »

I.2 · Principes et objectifs

Les quatre principes DevOps : CAMS

C

Culture

une équipe, un objectif commun : le service rendu à l'utilisateur

Dev et Ops préparent ensemble la mise en production.

A

Automatisation

les machines font les tâches répétitives et risquées

build, tests et déploiement lancés à chaque modification

M

Mesure

on mesure pour décider et réagir vite

taux d'erreur, temps de réponse, fréquence des livraisons

S

Partage

on partage connaissances, outils et retours d'expérience

un bilan d'incident sans chercher de coupable

CAMS : acronyme proposé par Damon Edwards et John Willis (2010) pour résumer la démarche.

🎙️ Ce que je peux dire

« Quatre lettres pour résumer DevOps : C comme Culture, A comme Automatisation, M comme Mesure, S comme Partage, en anglais Sharing. Remarquez qu'on retrouve les leviers que vous avez proposés dans la situation-problème. »

I.4 · Besoin d'industrialisation

La chaîne industrialisée : CI et CD

Intégration continueContinuous Integration · CI

À chaque modification envoyée dans Git, le code est construit et testé automatiquement.

Retour en quelques minutes : ✔ ou ✖

Livraison continueContinuous Delivery · CD

Chaque version validée est prête à partir en production. Un humain décide du moment.

un clic pour déployer

Déploiement continuContinuous Deployment · CD

Chaque version validée part automatiquement en production, sans intervention.

exige des tests et une supervision très fiables

Outils courants : GitLab CI, GitHub Actions, Jenkins. Et pour emballer l'application de façon identique à chaque étape : les conteneurs, donc Docker.

🎙️ Ce que je peux dire

« Trois termes à ne pas confondre. Intégration continue : on construit et on teste à chaque modification. Livraison continue : la version est prête, un humain appuie sur le bouton. Déploiement continu : même le bouton est automatique. »

Un hyperviseur découpe un serveur physique en plusieurs machines virtuelles (VM). Chaque VM a son propre système d'exploitation complet.

🎙️ Ce que je peux dire

« La virtualisation a été une révolution : un seul serveur physique héberge plusieurs machines virtuelles, isolées les unes des autres. Mais chaque VM contient un système d'exploitation entier. Pour une petite application web, c'est lourd. D'où la question : a-t-on vraiment besoin d'un OS complet pour isoler une application ? »

Les durées de démarrage citées sont des ordres de grandeur : elles varient selon l'OS et le matériel.

II.3 · Concepts de base

Étape 3 : la conteneurisation

Conteneur 1
app + libs
Conteneur 2

app + libs
Moteur de conteneurs
OS hôte · noyau partagé
Hardware

Un conteneur est un processus isolé qui s'exécute sur l'hôte avec son propre système de fichiers, son réseau et ses limites de ressources. Il partage le noyau du système hôte.

  • Il n'embarque pas d'OS complet : seulement l'application et ses dépendances.
  • Il démarre comme un programme : en général en une seconde ou moins.
  • Sous Linux, l'isolation repose sur le noyau : namespaces (ce que le processus voit) et cgroups (ce qu'il peut consommer).

🎙️ Ce que je peux dire

« Voici l'idée des conteneurs. Un seul système d'exploitation, l'hôte. Au-dessus, un moteur de conteneurs. Chaque conteneur contient seulement l'application et ses bibliothèques. Ce n'est pas une machine : c'est un processus de l'hôte, isolé grâce à des mécanismes du noyau Linux. »

III.7 · Mise en place d'une solution Docker

Comment Docker fonctionne : 4 notions

Ce qui se passe avec docker run nginx :

  1. le client envoie la demande au moteur ;
  2. image absente ? le moteur la télécharge depuis le registry ;
  3. le moteur crée le conteneur à partir de l'image ;
  4. le conteneur démarre.

Moteur arrêté = le client ne peut rien faire (« Cannot connect to the Docker daemon »).

🎙️ Ce que je peux dire

III.10 · Dockerfile et création d'images

Notre premier Dockerfile, construit et exécuté

app.py · mini-serveur web (bibliothèque standard Python)

import http.server, os MSG = os.environ.get("APP_MSG", "Bonjour") class H(http.server.BaseHTTPRequestHandler): def do_GET(self): self.send_response(200); self.end_headers() self.wfile.write(f"<h1>{MSG} depuis le conteneur !</h1>".encode()) http.server.HTTPServer(("0.0.0.0", 80), H).serve_forever()

Dockerfile (même dossier)

FROM python:3.12-slim WORKDIR /app COPY app.py . RUN mkdir -p /app/logs ENV APP_MSG="Bonjour HESTIM" EXPOSE 80 CMD ["python3", "app.py"]

EXÉCUTÉ Docker 29.4.3

$ docker build -t mon-app:1.0 . #7 [3/4] COPY app.py . #8 [4/4] RUN mkdir -p /app/logs #9 naming to docker.io/library/mon-app:1.0 done $ docker run -d -p 8080:80 --name web mon-app:1.0 30055a698c33f14085f0746172a25499e207205c… $ curl -s localhost:8080 <h1>Bonjour HESTIM depuis le conteneur !</h1> $ docker history mon-app:1.0 CREATED BY SIZE CMD ["python3" "app.py"] 0B EXPOSE [80/tcp] 0B ENV APP_MSG=Bonjour HESTIM 0B RUN /bin/sh -c mkdir -p /app/logs 24.6kB COPY app.py . 12.3kB WORKDIR /app 8.19kB

-t mon-app:1.0 = nom et étiquette · . = le dossier courant (le « contexte de build »). ENV, EXPOSE et CMD pèsent 0 octet : ce sont des métadonnées.

🎙️ Ce que je peux dire

« Voici un Dockerfile complet. docker build -t donne un nom à l'image ; le point final désigne le dossier courant. Chaque instruction devient une étape. Puis docker run, et le navigateur affiche notre message. docker history montre les couches. »

🖥️ Démonstration

Créer les deux fichiers, puis docker build -t mon-app:1.0 . et docker run -d -p 8080:80 --name web mon-app:1.0. Essayer -e APP_MSG="Salam" au lancement.

III.10 · Dockerfile et création d'images

Bonnes pratiques pour écrire un Dockerfile

Une base légère et versionnée

python:3.12-slim plutôt que python:latest : image plus petite, version maîtrisée.

Profiter du cache

copier d'abord les fichiers qui changent peu (dépendances), puis le code : les couches inchangées sont réutilisées.

Un fichier .dockerignore

exclure .git, fichiers temporaires, secrets : ils n'entrent pas dans l'image.

Aucun secret dans l'image

les mots de passe se passent au lancement (-e, secrets), jamais dans le Dockerfile.

Un processus par conteneur

le site dans un conteneur, la base dans un autre, reliés par un réseau.

Éviter root

créer un utilisateur et utiliser USER : moins de dégâts en cas de faille.

🎙️ Ce que je peux dire

« Six règles simples. Une image de base légère avec une version précise. L'ordre des instructions pour profiter du cache. Un .dockerignore. Jamais de secret dans l'image. Un processus par conteneur. Et un utilisateur non-root quand c'est possible. »

✅ Vérificationdocker logs mariadb se termine par « ready for connections »
⚠️ Erreur possiblemot de passe root absent : le conteneur s'arrête. Changer un -e après coup ne modifie pas une base déjà créée.
❓ Questionpourquoi pas de -p ? → seul GLPI accède à la base, par le réseau

🎙️ Ce que je peux dire

« Chaque ligne a un rôle. Le nom mariadb, c'est l'adresse que GLPI utilisera. Le volume est branché sur /var/lib/mysql, où MariaDB range ses fichiers. Les variables demandent à l'image de créer la base et l'utilisateur au premier démarrage. Pas de -p : la base reste privée. »

Mots de passe en clair pour le TP ; en production : fichier .env non versionné ou secrets. Les logs affichent deux fois « ready for connections » (initialisation, puis démarrage définitif) : attendre le second.

Lancer l'application GLPI

Ce que crée cette étape : le conteneur GLPI, publié sur 8080

🎯 Objectifexposer GLPI sur le port 8080 et le relier à la base
🧠 Pourquoi ?c'est l'application des utilisateurs : elle doit être joignable et trouver la base par son nom
🔍 Explication--network glpi-net = même réseau que la base · GLPI_DB_HOST=mariadb = le nom du conteneur · les 5 variables GLPI_DB_* déclenchent l'installation automatique
✅ Vérificationdocker logs -f glpi (Ctrl+C pour quitter) · docker exec glpi getent hosts mariadb
⚠️ Erreur possible« port is already allocated » → -p 8081:80 · base introuvable → réseau différent ou nom mal écrit
❓ Questionet sans --network glpi-net ? → le nom « mariadb » ne serait pas résolu

🎙️ Ce que je peux dire

« Même structure, deux différences : on publie le port 8080 pour les utilisateurs, et on donne à GLPI les informations de connexion. L'hôte de la base s'appelle simplement mariadb, grâce au réseau. Au premier démarrage, l'image installe elle-même la base : suivez-le avec docker logs -f. »

Variables et chemin /var/glpi conformes à la documentation officielle de l'image. Si GLPI démarre avant que MariaDB soit prête, docker restart glpi.

Atelier · Étape 5

Supprimer, recréer… et retrouver ses données

docker rm -f mariadb glpi # supprimer les 2 conteneurs docker ps -a # plus aucun conteneur docker volume ls # les volumes sont là # relancer exactement les commandes des étapes 2 puis 3

Les conteneurs disparaissent, les volumes restent

🎯 Objectifprouver que les données ne dépendent pas des conteneurs
🧠 Pourquoi ?mettre à jour une application = remplacer ses conteneurs ; les données doivent survivre
🔍 Explicationdocker rm ne supprime jamais un volume nommé : il faut docker volume rm
✅ Vérificationaprès recréation, le ticket « Imprimante du labo en panne » est toujours là
⚠️ Erreur possibledocker volume rm glpi-db : refusé si utilisé (« volume is in use ») ; une fois accepté, données perdues
❓ Questionmettre à jour GLPI, c'est donc… ? → recréer le conteneur avec une image plus récente, mêmes volumes, après une sauvegarde

🎙️ Ce que je peux dire

« Moment de vérité. Je supprime les deux conteneurs : plus rien ne tourne. Mais les volumes sont là. Je relance les mêmes commandes… et mon ticket est toujours là. C'est le principe des mises à jour en conteneurs : on jette le conteneur, on garde les données. »

GLPI tourne avec notre image

🎯 Objectifune image GLPI « HESTIM » avec nos limites PHP
🧠 Pourquoi ?une configuration écrite dans un Dockerfile est versionnée et rejouable ; une modification faite à la main dans un conteneur disparaît avec lui

✅ Vérificationdocker exec glpi php -r 'echo ini_get("upload_max_filesize"), PHP_EOL;' → 20M

🎙️ Ce que je peux dire

« Nous ne réinventons pas GLPI : nous partons de l'image officielle et nous ajoutons seulement notre configuration PHP. Trois lignes. On construit, on remplace le conteneur, et grâce au volume rien n'est perdu. C'est exactement ce que fait une équipe DevOps. »

Toute l'architecture dans un seul fichier : Docker Compose

services: mariadb: image: mariadb:11.4 restart: unless-stopped environment: MARIADB_ROOT_PASSWORD: RootEnset2026 MARIADB_DATABASE: glpi MARIADB_USER: glpi MARIADB_PASSWORD: GlpiEnset2026 volumes: [ "glpi-db:/var/lib/mysql" ] networks: [ glpi-net ] healthcheck: test: ["CMD", "healthcheck.sh", "--connect", "--innodb_initialized"] interval: 10s retries: 10
glpi: image: glpi/glpi:11.0 restart: unless-stopped depends_on: mariadb: { condition: service_healthy } environment: GLPI_DB_HOST: mariadb GLPI_DB_PORT: 3306 GLPI_DB_NAME: glpi GLPI_DB_USER: glpi GLPI_DB_PASSWORD: GlpiEnset2026 ports: [ "8080:80" ] volumes: [ "glpi-data:/var/glpi" ] networks: [ glpi-net ] volumes: { glpi-db: {}, glpi-data: {} } networks: { glpi-net: {} }
docker compose up -d docker compose ps docker compose logs -f docker compose down

Fichier compose.yaml. Chaque ligne correspond à une option vue : -e, -v, -p, --network, --restart. Le healthcheck fait attendre GLPI jusqu'à ce que la base soit prête.

docker compose down -v supprime aussi les volumes, donc les données.

Validé avec docker compose config (Compose v5.1).

🎙️ Ce que je peux dire

« Tout ce que nous avons tapé tient dans ce fichier : c'est de l'infrastructure décrite comme du code. Une seule commande crée le réseau, les volumes et les deux conteneurs, dans le bon ordre. »
